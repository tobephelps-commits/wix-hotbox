<objective>
Implement priority-based polling tiers, efficient batch API queries, and daemon resilience so the sync loop can run continuously with differentiated poll frequencies for hot vs normal products.

Purpose: The current system polls all products at the same interval (60 min). High-demand products need more frequent checks (5-15 min), while stable products can poll less often. Batch querying reduces API call volume. Daemon resilience prevents silent failures during long-running operation.
Output: Tiered polling with hot/normal/slow priorities. Batch inventory fetching. Auto-recovery from transient errors. Health status tracking.
</objective>

<task type="auto">
  <name>Task 1: Add priority tiers and batch polling to monitor</name>
  <files>scripts/monitor/types.ts, scripts/monitor/poller.ts, scripts/monitor/store.ts</files>
  <action>
  In types.ts, add a `PollPriority` type: `'hot' | 'normal' | 'slow'`.

  Extend TrackedProduct with optional fields:
  - `priority?: PollPriority` (default: 'normal')
  - `lastPolledAt?: string` (ISO timestamp of last successful poll)

  Extend MonitorConfig with optional fields:
  - `hotIntervalMinutes?: number` (default: 15)
  - `slowIntervalMinutes?: number` (default: 120)
  (existing pollIntervalMinutes serves as 'normal' interval, default 60)

  In poller.ts, refactor pollOnce() to support selective polling:
  1. Add a new function `getProductsDueToPoll(products: TrackedProduct[], config: MonitorConfig): TrackedProduct[]` that checks each product's lastPolledAt against its priority's interval. A product is "due" if now - lastPolledAt >= interval for its priority tier (or if lastPolledAt is undefined — always poll on first run).
  2. Modify pollOnce() to accept an optional `productsOverride?: TrackedProduct[]` parameter. If provided, poll only those products. If not provided, poll all (backward compatible with existing `npm run monitor -- poll` behavior).
  3. Add a new function `pollDue(config: MonitorConfig, onAlerts?): Promise` that calls getProductsDueToPoll to determine which products need polling, then polls only those. After each product is polled, update its lastPolledAt in the tracked products store.
  4. Use getInventoryBatch() from the SanMar service when polling multiple products to reduce API calls. Group product styles into batch requests of up to 200 partIds. Fall back to individual getStyleInventory() calls only when batch returns errors for specific styles.

  In store.ts, add `updateProductLastPolled(style: string, timestamp: string, config: MonitorConfig)` that updates a single product's lastPolledAt field in the tracked products JSON without loading/saving the entire file unnecessarily (load, find, update, save).

  Keep the existing pollOnce() and startPolling() functions working as before — pollDue is additive.
  </action>
  <verify>npx tsc --noEmit passes. Verify that existing `npm run monitor -- poll` still works (polls all products). Verify getProductsDueToPoll returns correct products based on priority/lastPolledAt.</verify>
  <done>PollPriority type defined. TrackedProduct has optional priority and lastPolledAt fields. pollDue() polls only products whose interval has elapsed. Batch querying groups styles. Existing pollOnce/startPolling unchanged.</done>

<task type="auto">
  <name>Task 2: Build resilient daemon loop with health tracking</name>
  <files>scripts/sync/sync-poller.ts</files>
  <action>
  Refactor startSyncLoop() to use the new priority-based polling:

  1. Replace the single setInterval with a faster tick loop (every 1 minute) that checks which products are due using pollDue(). This way hot products (15 min) and normal products (60 min) are handled naturally without separate timers.

  2. Add health tracking state (module-level, not persisted):
  ```
  SyncHealth {
    startedAt: string             // ISO when daemon started
    lastTickAt: string            // ISO of last tick
    lastSuccessAt: string | null  // ISO of last successful poll cycle
    consecutiveErrors: number     // Resets on success
    totalCycles: number           // Total tick count
    totalErrors: number           // Lifetime error count
    productsPolled: number        // Products polled this session
  }
  ```

  3. Add error recovery: if a tick fails (API timeout, network error), catch the error, increment consecutiveErrors, log a warning, and continue to next tick. After 5 consecutive errors, log an error-level message with details. Never crash the loop — the store owner runs this unattended.

  4. Export a `getSyncHealth(): SyncHealth` function for the CLI and preview server to query daemon status.

  5. Keep the existing syncOnce() function unchanged — it's used by `npm run sync:run` for single-shot execution.

  6. Add a new `startSmartSyncLoop(monitorConfig, syncConfig)` function that uses the tick-based approach. Keep `startSyncLoop()` as-is for backward compat but have it log a deprecation notice suggesting startSmartSyncLoop.
  </action>
  <verify>npx tsc --noEmit passes. Run `npx tsx scripts/sync/manage.ts config` to verify the module loads without error.</verify>
