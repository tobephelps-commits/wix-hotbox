<task type="auto">
  <name>Task 1: Add error tracking, on-hold status, and retry metadata to order types and store</name>
  <files>scripts/orders/types.ts, scripts/orders/order-store.ts</files>
  <action>
  **types.ts changes:**

  1. Add `'on-hold'` to the `OrderStatus` type union. This is for orders that need human attention (vendor out of stock, failed PO, payment issue). Place it after `'new'` in the union.

  2. Update `ORDER_STATUS_TRANSITIONS` to include `on-hold`:
     - `'new'` can transition to `['ordered', 'on-hold', 'cancelled']`
     - `'ordered'` can transition to `['received', 'on-hold', 'cancelled']`
     - `'on-hold'` can transition to `['new', 'ordered', 'cancelled']` (allows resuming from where it was put on hold)
     - Every non-terminal status except `on-hold` itself gets `on-hold` added to its valid transitions

  3. Update `ORDER_STATUSES` array to include `'on-hold'` after `'new'`.

  4. Add an `OrderError` interface:
     ```typescript
     export interface OrderError {
       /** What operation failed */
       operation: 'sync' | 'cart-fill' | 'print-invoice' | 'print-label' | 'status-update';
       /** Error message */
       message: string;
       /** ISO-8601 timestamp of failure */
       timestamp: string;
       /** Number of retry attempts so far */
       retryCount: number;
       /** Whether this error has been resolved */
       resolved: boolean;
     }
     ```

  5. Add optional fields to the `Order` interface:
     - `errors?: OrderError[]` — tracked errors for this order
     - `lastSyncError?: string` — last WIX sync error message (quick indicator)

  **order-store.ts changes:**

  1. Add `addOrderError(id: string, error: Omit<OrderError, 'retryCount' | 'resolved'>): Promise<Order>` function:
     - Loads store, finds order by id
     - Initializes `order.errors` array if undefined
     - Appends error with `retryCount: 0, resolved: false`
     - Updates `order.updatedAt`
     - Saves store, returns order
     - Throws if order not found

  2. Add `resolveOrderError(id: string, operation: OrderError['operation']): Promise<Order>` function:
     - Finds the most recent unresolved error matching the operation
     - Sets `resolved: true` on it
     - Clears `lastSyncError` if operation is 'sync'
     - Returns updated order

  3. Add `getOrdersWithErrors(): Promise<Order[]>` function:
     - Returns all orders that have at least one unresolved error in their `errors` array
     - Sorted by most recent error timestamp descending

  4. In the `loadOrders` migration block, add: `if (!o.errors) o.errors = [];` for backward compatibility.

  5. Add `getOrderSummary(): Promise<Record<OrderStatus, number>>` function:
     - Loads all orders
     - Returns a record counting orders per status (e.g., `{ new: 5, ordered: 3, ... }`)
     - Include `errored: N` as an extra key for orders with unresolved errors (not a status, just a count)

  Do NOT modify the existing `updateOrderStatus`, `addOrder`, or `upsertWixOrder` signatures — only add new functions.
  </action>

<task type="auto">
  <name>Task 2: Add retry logic to WIX sync and create summary/error API endpoints</name>
  <files>scripts/orders/wix-order-sync.ts, scripts/pipeline/preview-server.ts, scripts/orders/index.ts</files>
  <action>
  **wix-order-sync.ts changes:**

  1. Add a `syncWithRetry(maxRetries = 3, baseDelayMs = 2000)` function:
     - Wraps `syncWixOrders()` in a retry loop
     - On failure of the WIX API fetch (the `getRecentOrders` call that currently aborts the entire sync):
       - Retry up to `maxRetries` times with exponential backoff: `baseDelayMs * 2^attempt` (2s, 4s, 8s)
       - Log each retry attempt: `[ORDER SYNC] Retry ${attempt}/${maxRetries} after ${delay}ms...`
       - If all retries exhausted, return the error result (don't throw)
     - Per-order errors (already handled by the try/catch in the for loop) are NOT retried — only the initial WIX API fetch
     - Update the `SyncResult` type to include `retriesUsed: number` (add to interface)

  2. Modify `syncWixOrders` to accept an optional `signal?: AbortSignal` parameter so callers can cancel a long-running sync. Check `signal.aborted` before each order processing iteration. If aborted, append "Sync cancelled by user" to errors and return early.

  3. Update `autoSync()` to call `syncWithRetry()` instead of `syncWixOrders()`.

  **preview-server.ts changes:**

  1. Add `GET /api/orders/summary` endpoint (add route matching before the `/api/orders/:id` catch-all):
     - Calls `getOrderSummary()` from order-store
     - Also calls `getOrdersWithErrors()` to get error count and list of order IDs with errors
     - Returns: `{ statusCounts: Record<OrderStatus, number>, errorCount: number, errorOrderIds: string[], lastSync: string }`
     - The `lastSync` value comes from `loadOrders().lastSync`

  2. Add `GET /api/orders/errors` endpoint:
     - Calls `getOrdersWithErrors()`
     - Returns `{ orders: Order[], count: number }` — only orders with unresolved errors, sorted by most recent error

  3. Modify the existing `POST /api/orders/sync` handler:
     - Call `syncWithRetry()` instead of `syncWixOrders()` (for non-reset syncs)
     - Include `retriesUsed` in the response

  4. Add `POST /api/orders/:id/resolve-error` endpoint:
     - Body: `{ operation: string }` — which error type to resolve
     - Calls `resolveOrderError(id, operation)`
     - Returns the updated order
     - 404 if order not found, 400 if no matching error

  **index.ts changes:**

  Export the new functions: `addOrderError`, `resolveOrderError`, `getOrdersWithErrors`, `getOrderSummary`, `syncWithRetry`. Also export the `OrderError` type.

  **Route matching:** Add these URL patterns to the route matcher at the top of the order endpoint section in preview-server.ts:
  - `/api/orders/summary` → case 'orders-summary'
  - `/api/orders/errors` → case 'orders-errors'
  - `/api/orders/:id/resolve-error` → case 'order-resolve-error'

  Make sure `/api/orders/summary` and `/api/orders/errors` are matched BEFORE the `/api/orders/:id` pattern (otherwise "summary" and "errors" would be interpreted as order IDs).
  </action>
